## 4. 设计思路

- **补丁怎么重放**：直接用我们的「8 个补丁提交」在 `v0.3.1` 上做三方合并/重放，再按路径拆成 6 个补丁。上游把 `app.rs` 拆成 `app/*.rs` 的那一步没法机械 patch，于是用「按上下文把 diff 的 hunk 迁移到新模块」的半自动方法（`tmp/port_app.py`）落 62/72 个 hunk，剩下 10 个手放；`skyward/src/ui.rs` 的 `run()` 改成 `Pages` 结构后，按 `open/begin/turn/*_told/effect` 手工移植。
- **服务发现取代写死服务表**：这是 0.3.1 的核心变化，好处是底包升级后服务名/顺序跟着系统走；代价是库路径由上游给，onyx 需要的 `/mnt/system/system/lib64` 不在里面（见第 5 节）。选择**改上游的库目录**而不是恢复写死服务表：保住自动发现的好处，同时让所有 `/vendor` HAL 都能拿到安装系统的库。
- **OMAPI 不再自己实现**：上游自带的桥在发现流程里自动起；user 0 仍是 gatekeeper 回退，不把 OMAPI 接进主路径。
- **版本号**：`v<上游版本>-onyx.<n>`，所以是 `v0.3.1-onyx.1`，不复用 0.3.0 的序号。

## 5. 踩过的坑

（每条按 现象 → 根因 → 解法 → 如何避免）

1. **keymint 启动即退出，data 打不开、没有锁屏**
   - 现象：开机停在解密页，`dmesg` 每秒一条 `keymint-service-qti: pid … ended: exit status: 1`，`/data` 不挂载；用户看到「data 没解开，没有锁屏」。
   - 根因：自动发现给 `/vendor` 程序的库目录只有 `/system/lib64:/vendor/lib64`；Android 17 recovery 没有 `libvndksupport.so`。手动跑：
     `CANNOT LINK EXECUTABLE "/vendor/bin/hw/android.hardware.security.keymint-service-qti": library "libvndksupport.so" not found: needed by /vendor/lib64/libhardware.so`
   - 解法：`crates/skyward-programs/src/secure.rs` 的 `VENDOR_LIBRARIES` 补上 `/vendor/lib64/hw`、`/mnt/system/system/lib64`、`/mnt/system/system/lib64/bootstrap`（与 0.3.0 写死的服务表一致）。刷入后 keymint 正常注册，`/data` 挂载、user 0 自动解开、锁屏回来。
   - 如何避免：换上游/底包时先手动带 `LD_LIBRARY_PATH` 跑 HAL，确认能驻留；Skyward 只记 `exit status: 1`，必要时临时把子进程 stderr 落盘。

2. **Windows 宿主打包器编不过**
   - 现象：`skyward-block` 的 `std::os::unix` / `libc::statvfs` 报错。
   - 根因：0.3.1 的 `described` 子命令把 `skyward-programs`（只面向 Android/Linux）拉进宿主依赖。
   - 解法：`described` 做成 Cargo feature（默认开），宿主用 `--no-default-features` 编；`build-pack.sh` 已改。
   - 如何避免：宿主与手机共用 workspace 时，只在手机侧用的子命令做 feature 门控。

3. **重放补丁时 data.rs 留下冲突标记**
   - 现象：第一次自动合并后 `data.rs` 仍有 `>>>>>>>`，编译报 `expected expression`。
   - 根因：手工解决冲突的脚本按 `ours/theirs` 标签匹配，而实际标签是临时文件名。
   - 解法：改为按行首 `<<<<<<<` / `=======` / `>>>>>>>` 位置解析；之后的冲突都用这种解析。教训写进脚本。
   - 如何避免：合并脚本不要依赖冲突标记的标签文字。

4. **刷机后 adb 一度完全消失**
   - 现象：keymint 重启循环后 `adb devices` / `fastboot devices` 都空。
   - 根因：未查清（很可能是恢复服务反复重试/重启导致 USB 重新枚举，或机器被手动重启）；强制重启后恢复。
   - 解法：请用户长按电源强制重启，回到 recovery 后继续抓日志。
   - 如何避免：遇到 USB 全空先确认设备是否还在开机循环，必要时让用户强制重启，不要反复 `adb kill-server`。

5. **旧 `settings.json` 兼容**
   - 现象：本以为升级后要重新输密码、重连 WLAN。
   - 根因：字段名未变，`Settings::read` 容忍未知/缺失字段。
   - 解法/验证：旧机器刷入后 user 0 自动解密、WLAN 自动连上，确认兼容。
   - 如何避免：改设置字段名时写迁移，或明确清 `/metadata/skyward`。

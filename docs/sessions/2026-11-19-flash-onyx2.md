# 把 v0.3.1-onyx.2 刷进真机（2026-11-19）

状态：已完成（刷入 + 版本核对通过；重启后未再连回电脑做 UI 复验）
关联版本：v0.3.1-onyx.1 → v0.3.1-onyx.2
关联提交：无代码改动（只刷机与记录）

## 1. TL;DR

用 `fastboot flash recovery` 把已发布的 `recovery.img`（`f1b7685e…9a7d38`）写进 onyx 的 recovery 分区，重启后 `/system/bin/recovery` 为 8,959,728 字节、sha256 `6e2c030e…6840`，与 onyx.2 构建记录一致，`/data` 自动打开（user 0 已解开）。刷完验证时误以 `recovery` 名字执行二进制，触发第二个 recovery 实例抢硬件，手机黑屏重启；重启后 USB 暂未枚举，未做 UI 复验。

## 2. 对话重点

- 用户要求：「帮我刷进手机里」。
- 刷机前设备已在 Skyward recovery（adb root），随后进入 fastboot（`fastboot devices` 见 `a759561 fastboot`）。
- 决策：按 `docs/04-install.md` 走 `fastboot flash recovery`，不在 recovery 内 `dd` 写正在运行的分区，不动 boot / system / super / userdata。
- 范围外但被提到：无。

## 3. 修复内容

无代码改动。本次只做镜像刷入与真机核对，产物与补丁均未改动。

## 4. 设计思路

- 为什么 fastboot：文档已把 `fastboot flash recovery` 作为唯一刷机路径；镜像正好是整分区 104,857,600 字节，写入整块，不存在「只写一部分」的问题；也是所有历史版本真机验证走的路。
- 为什么不 `dd`：recovery 正在从该分区运行，虽然内核与 ramdisk 已加载进内存，但没有必要引入「写活分区」的风险；fastboot 写失败时仍可再刷。
- 回滚成本：原厂 `recovery-stock-OS4.0.2.0.XOLCNXM.img`（`ce538507…3357`）就在手上，任何时候可刷回。

## 5. 踩过的坑

**现象**：刷完在 recovery 里执行 `/system/bin/recovery --version` 想读版本号，命令没有输出，随后手机黑屏重启，adb / fastboot 全部消失（两次会话中同一操作各触发一次）。

**根因**：skyward 用 `argv[0]` 判断自己是不是被 init 拉起的 recovery；二进制在镜像里的名字就是 `recovery`，于是忽略 `--version` 子命令，直接走 recovery 主流程，起了第二个实例，和已有实例抢触摸 / 安全世界硬件。即 `docs/06-pitfalls.md` 第 3 条在真机上的又一次复现，只是这次触发者是我自己在做验收。

**解法**：不要在设备上执行 `/system/bin/recovery …`；核对版本改看**文件大小 + sha256**（`ls -l /system/bin/recovery`、`sha256sum`），或 `dmesg` 里的 `skyward:` 行。要跑子命令就 `adb push` 成 `/tmp/skyward` 之类的名字。

**如何避免**：验收脚本禁止以镜像内文件名直接调用；版本判断只认哈希。

## 6. 验证与证据

刷前：

```text
sha256sum recovery.img
f1b7685e60498e92a19cda4c27202b4e470074702dcc8f8991376bb4429a7d38  recovery.img   # 与 SHA256SUMS 一致
fastboot getvar product      -> onyx
fastboot getvar current-slot -> b
```

刷入：

```text
fastboot flash recovery recovery.img
Sending 'recovery' (102400 KB)                     OKAY [  3.141s]
Writing 'recovery'                                 OKAY [  0.069s]
```

刷后（`fastboot reboot recovery` 后设备以 `recovery` 状态被 adb 识别）：

```text
ls -l /system/bin/recovery
-rwxr-xr-x 1 root root 8959728 1970-01-01 00:00 /system/bin/recovery
sha256sum /system/bin/recovery
6e2c030e0e216845a4ec242ac8a7ff99f7448fa4e0ce9c06d56be0442ea06840
```

该大小 / 哈希与 `docs/00-status.md` 记录的 onyx.2 内含 skyward 一致，确认运行的是新镜像。

启动日志：

```text
skyward: loaded /vendor_dlkm/lib/modules/qca_cld3_wcn7750.ko
skyward: the check of /dev/block/dm-9 ended with 0
skyward: /dev/block/dm-9 holds f2fs at /data
skyward: the users whose own files are still closed: []
skyward: mtp: the computer opened a session
```

`/data` 自动打开、user 0 CE 自动解开（旧版保存的锁屏密码），MTP 已建立 —— 说明换镜像后设备级解密路径正常。

**未验证**：

- 重启进系统后的 UI / 触摸 / WLAN 等（手机黑屏重启后再未被电脑枚举，未再进 recovery 看首屏）；
- 补丁 0007 的整包 OTA 流程（本次只刷 recovery 分区，没有装包）；
- 底包一致性：本次 recovery 的 `/proc/cmdline` 里 `swinfo.fingerprint=onyx:15/OS4.0.3.1.XOLCN:user`，与文档记录的 `OS4.0.2.0.XOLCNXM` 不一致（刷之前那次启动也一样）。需确认设备是否已更新过底包。

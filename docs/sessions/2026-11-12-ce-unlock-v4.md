# v4：user 0 的 CE 解开（2026-11-12）

状态：已完成
关联版本：v0.2.0-onyx.3 → v0.2.0-onyx.4
关联提交：`patches/0003-onyx-ce-fallback.patch`（仓库首次提交）

## 1. TL;DR

不再走 weaver / OMAPI：发现 user 0 在 `/data/system_de/0/spblob/` 下还有第二份绑 gatekeeper 的 protector，用同一个锁屏密码就能拿到 SP。`data.rs` 加回退后，真机上 `recovery.img`（`b41bee5b…f1f83f`）的「解密」页输入密码即可读相册和微信，`/data` 未被修改。

## 2. 对话重点

- 用户反馈「还是解密不了 data」，并强调数据很重要；
- 用户反馈「有时会黑屏」；
- 决策：
  - 先做 OMAPI → SE HAL 桥（方案 A），打通到 weaver 能调 `getReaders/getReader/isSecureElementPresent`，但 SE HAL `init()` 卡住；
  - 转向 gatekeeper 回退（方案 B），不再碰 eSE；
  - 补丁只改 `data.rs`，不碰 `keymint` / `gatekeeper` / `weaver` 的二进制；
  - 解密验证坚持只读挂载、不写 `/data`。
- 范围外：WiFi 页（未做）、user 999（明确不做）。

## 3. 修复内容

| 文件 | 改了什么 | 为什么 |
| --- | --- | --- |
| `crates/skyward-crypto/src/data.rs` | `protector()` 拆成 `protector_ids()` / `protector_named()` | 需要枚举同一用户的全部 protector |
| 同上 | `open_user_files()` 在 `WeaverUnusable` 时遍历其他 `Secdiscardable + lock` 的 protector，用同一 credential 重试 | user 0 的第二份 protector 绑 gatekeeper |
| 同上 | 抽出 `open_with_protector()` | 保持原逻辑可复用，减少回退路径的差异 |
| 同上 | 新增 `WeaverUnusable` 错误 | 区分「weaver 不可用」与「凭据错误」，只在真正不可用时回退 |
| `crates/skyward-binder/*` + `crates/skyward/src/omapi.rs` | OMAPI 服务端 + SE HAL 转发 + `skyward omapi` / `se` | 方案 A 的产物；保留为实验 / 排错 |
| `crates/skyward/src/main.rs` | 加两个子命令 | 同上 |

## 4. 设计思路

- **问题本质**：CE key 被 SP 派生的 file secret 软件包裹；SP 存在 `spblob` 里，由 protector 的 secret 打开。weaver 只是「保管 secret 的一种方式」，不是唯一方式。
- **方案 A（OMAPI 桥）**：能通到 weaver，但 SE HAL 的 `init()` 等 eSE TA，继续碰 TEE 有黑屏风险；收益只覆盖 weaver 路径，成本高。
- **方案 B（gatekeeper 回退）**：系统自己留了第二份 `.secdis` + `.pwd`，salt / scrypt 参数相同；gatekeeper 校验密码后返回 note，keymint 解 `spblob` 得到同一个 SP。不碰 eSE、不改数据、改动小。
- **关键取舍**：优先「不增加黑屏风险 + 不碰数据」，放弃「一次覆盖所有用户」；user 999 留给以后。
- **不选直接 APDU**：NXP applet 协议私有，写错可能复位 eSE。

## 5. 踩过的坑

1. **OMAPI 服务名不是 `omapiSeService`**：现象是 weaver 一直 `Failed to start omapiSeService`；根因那只是 NXP 的日志文本，实际 `checkService("android.se.omapi.ISecureElementService/default")`；解法按真实名字注册；预防反汇编 `libjc_keymint_transport_nxp.so` 确认。
2. **stability 必须 3**：1/2/16/32/48 都被 `Stability: Can only set known stability` 拒；解法用 3，回调对象也带 3。
3. **AIDL 方法编号从 1 开始**：按 0 写会错位；解法 `getReaders=1, getReader=2, isSecureElementPresent=3`。
4. **裸回包不能带 status 字**：`_NTF` / 版本 / 哈希 / pid / ping 的回包格式与普通事务不同；解法按 libbinder 布局回。
5. **SE HAL `init()` 卡住**：eSE TA 未起来；继续碰 TEE 会黑屏；解法放弃方案 A。
6. **CE key 目录没有 `.weaver` 文件**：一开始误判「不需要 weaver」；实际 weaver 信息在 `spblob/*.weaver`，不在 CE key 目录；教训是先把目录列全再下结论。
7. **user 999 只有 weaver 绑定**：回退条件 `Secdiscardable + lock` 不满足；明确写进限制。
8. **文档条目数 998 vs 996**：v2 的数字没同步；以 `skyward-pack list` 为准。

## 7. 未完成 / 下一步 / 风险

- **user 999**：需要让 weaver 在 recovery 里真正访问 eSE（方案 A 的 `init()` 问题），风险高，暂不做。
- **WLAN / 振动**：缺配置，需要真机核对。
- **黑屏**：两次对应 `ctl.stop recovery`；其余原因未查清。
- **换底包**：本补丁依赖 `.secdis` + `.pwd` 的布局与 salt / scrypt 参数；换底包必须重新确认。
- 风险：`data.rs` 的回退只在 `WeaverUnusable` 时触发；若 weaver 报的是「凭据错误」而不是「不可用」，不会回退，这是有意的——避免把错误密码当成环境问题。
